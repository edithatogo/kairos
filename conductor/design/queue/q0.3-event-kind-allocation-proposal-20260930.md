# Q0.3 Flow event-kind allocation proposal

**Status:** Proposal only. Numeric values below are provisional pending explicit Kairos core-owner confirmation. Runtime implementation is not implemented; no core-contract change has been made, and no owner acknowledgment has been received.

**Inspected Kairos commit:** `04c492984d13c559e335390d1a1641f943c73f01`.

## Source facts at the inspected commit

`crates/kairo-ecs-types/src/lib.rs` declares `EventKind` with the sole variant `Custom(u32)`. `EventKind::custom(code)` wraps any `u32`, and `EventKind::code()` returns that value unchanged. Neither this type nor `ScheduleRequest::try_new` validates or reserves event-kind numbers.

The scheduler contract orders events by `(time_ticks ASC, priority ASC, sequence ASC)` (`conductor/contracts/core-contract.md`). This proposal does not change that order.

The known named numeric use is `BEHAVIOR_UPDATE_EVENT_KIND = 3_001` in `crates/kairo-ecs-abm/src/lib.rs`. ABM's `schedule_behaviour` accepts an arbitrary `u32` and wraps it as `EventKind::Custom(kind)`. The current `BehaviorSimulation::run_for` invokes the behavior for every dispatched event with a live entity; it does not route by `kind.code()`. DES accepts an `EventKind` in its scheduling context and returns dispatched events from `run_trajectory`; it does not route trajectory steps by kind code. Code inspection also found these raw producers and projections:

| Surface | Source behavior observed at the inspected commit |
| --- | --- |
| Core `SchedulerFacade` | `schedule_custom` accepts any `u32` and wraps it as `EventKind::Custom`; `RecordingScheduler` records the raw numeric value. |
| FFI | `schedule_at` accepts a `u32` kind and wraps it as a custom event. |
| CLI | Scenario manifests parse `expected_kind_order` as numeric expected output codes. The replay fixture schedules fixed sample kinds through an internal helper and compares them with that expected order; the manifest values are not scheduler ingress. |
| Debugger | Trace encoding/parsing uses `custom:<u32>`; event-kind breakpoints can carry raw custom values. |
| Visualization | Snapshot/event projections read `event.kind.code()`; tests also construct raw custom values. |
| Arrow | `EventLogRecord::dispatched` writes `custom:<code>` to the existing `event_kind` field. |
| Benchmarks and tests | Several generate or assert arbitrary numeric kinds, including values derived from loop indices. They are examples of callers, not a complete registry. |

The source paths reviewed for those surfaces are `crates/kairo-ecs-core/src/lib.rs`, `crates/kairo-ecs-ffi/src/lib.rs`, `crates/kairo-ecs-cli/src/scenario.rs`, `crates/kairo-ecs-cli/src/main.rs`, `crates/kairo-ecs-debug/src/lib.rs`, `crates/kairo-ecs-viz/src/lib.rs`, and `crates/kairo-ecs-bench/src/lib.rs`, in addition to the ABM, DES, Arrow, and types paths named above. The CLI row is a consumer of expected codes, not a raw scheduling producer. This inventory is a bounded source review, not proof that every downstream or external caller has been found.

A read-only `git grep` at the inspected source commit found no literal uses of `4000–4003` and no event-kind allocation registry in `crates/` or `conductor/contracts/`. This supports using the values as candidates for a new local reservation, but it does not establish global uniqueness: raw callers accept arbitrary `u32` values and downstream consumers are outside this repository search.

The Arrow event-log projection in `crates/kairo-ecs-arrow/src/lib.rs` serializes a dispatched kind as the string `custom:<code>` in the existing `event_kind` field. The existing `event_log.v1` representation therefore exposes the numeric code through its current encoding. This proposal does not change its schema, field, or encoding.

Because raw scheduler and ABM/DES callers can supply any `Custom(u32)`, the current API cannot globally prevent another caller from using a proposed Flow number. A private Flow facade can reject conflicts at its own boundary only if every Flow scheduling request passes through that facade. This is not a global restriction on raw `Scheduler` users.

## Candidate allocation, pending core-owner decision

Consider `4000–4003` as provisional candidate codes for internal Flow event kinds. They are numerically distinct from the named ABM constant `3001`, but the inspected source contains unrestricted raw producers and no global allocation registry. These candidates are not source-wide or globally unique today; the Kairos core owner must record and confirm an allocation before they can be treated as reserved.

| Candidate internal name | Candidate `Custom(u32)` code | Flow purpose |
| --- | ---: | --- |
| `FLOW_COMMAND_DISPATCH_EVENT_KIND` | 4000 | Dispatch one buffered Flow command through the Flow runtime boundary |
| `FLOW_WORK_COMPLETION_EVENT_KIND` | 4001 | Deliver a scheduled work-completion event |
| `FLOW_WAITING_DEADLINE_EVENT_KIND` | 4002 | Wake a Flow continuation when its waiting deadline is reached |
| `FLOW_CONTINUATION_NOTIFICATION_EVENT_KIND` | 4003 | Notify a registered Flow continuation |

If the candidates are confirmed, `FlowRuntime` must own a private `Scheduler`, expose no mutable scheduler or generic `EventKind` scheduling path, and route all internal events through private named constants. Every public Flow command/event ingress must reject caller-supplied custom values in `4000–4003`; only the runtime's internal scheduling path may use them. Tests must exercise each external ingress and handler command sink. This provides a FlowRuntime-local guarantee only. Raw `Scheduler`, core facade, FFI, CLI, standalone DES/ABM, debugger, visualization, and downstream users remain able to emit the same numeric values unless separately changed by their owners.

## Proposed core-contract text for owner review

> **Proposed; not yet adopted.** If confirmed by the Kairos core owner, allocate `EventKind::Custom(4000..=4003)` to internal Flow runtime events, owned by the Kairos core owner in coordination with the Flow/Track 03 owner. The symbolic names are `FLOW_COMMAND_DISPATCH_EVENT_KIND = 4000`, `FLOW_WORK_COMPLETION_EVENT_KIND = 4001`, `FLOW_WAITING_DEADLINE_EVENT_KIND = 4002`, and `FLOW_CONTINUATION_NOTIFICATION_EVENT_KIND = 4003`. The codes are candidates only until this allocation is recorded and confirmed; consumers must use named constants rather than duplicate numeric literals. FlowRuntime must own a private scheduler, reject caller-supplied custom values from every public Flow ingress in this range, and schedule its internal events only through a private facade. This is not global validation for raw Scheduler, core facade, FFI, CLI, ABM/DES, debugger, visualization, or downstream users. Preserve `EventKind::Custom(u32)`, `EventKind::code()` behavior, scheduler ordering by `(time_ticks, priority, sequence)`, and the existing `event_log.v1` schema and encoding. Raw callers may continue to emit these values in the unchanged `custom:<code>` projection; the reserved meaning applies only within FlowRuntime.
