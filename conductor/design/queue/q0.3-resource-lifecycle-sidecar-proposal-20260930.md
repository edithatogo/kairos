# Q0.3 resource lifecycle sidecar proposal

**Status:** Proposed for owner review; not adopted. No runtime or Arrow implementation is included.

## Purpose and compatibility

Define an additive `resource_lifecycle.v1` sidecar for resource state transitions. It is separate from `event_log.v1`; the existing event log schema, fields, generational event handle encoding, and `custom:<code>` event-kind encoding remain unchanged. This proposal does not define portable checkpoint, snapshot, or restore semantics. The queue spec assigns those semantics to Track 22's later coordinated contract; its current handoff leaves real checkpoint state and resume semantics as follow-up work.

FlowRuntime's adopted event-kind values 4000–4003 remain FlowRuntime-local. This sidecar does not create a global event-kind registry or change scheduler ordering.

## Proposed Arrow record

Stream name: `kairo_ecs.resource_lifecycle.v1`; `schema_version` is `UInt16`, required, and equals `1` for this version. Each row describes one committed state transition, with fields below. Nullability is part of the proposed contract.

| Field | Arrow type | Nullable | Meaning |
|---|---|---:|---|
| `schema_version` | `UInt16` | no | Sidecar schema version, `1`. |
| `run_id` | `Utf8` | no | Deterministic simulation run/session identifier; joins to `event_log.v1.run_id`. |
| `causal_event_id` | `FixedSizeBinary(12)` | no | Generational event handle that caused the transition; joins to `event_log.v1.event_id`. |
| `transition_ordinal` | `UInt32` | no | Zero-based order among transitions emitted for the same `(run_id, causal_event_id)`. |
| `time_ticks` | `FixedSizeBinary(16)` | no | Unsigned 128-bit tick value, little-endian, matching `event_log.v1.time_ticks`. |
| `time_scale` | `Utf8` | no | `ticks`, matching the joined `event_log.v1` row. |
| `resource_id` | `FixedSizeBinary(12)` | no | Generational resource handle. |
| `request_id` | `FixedSizeBinary(12)` | yes | Generational request/claim handle when the transition concerns one request. |
| `owner_id` | `FixedSizeBinary(12)` | yes | Generational owner/entity handle when applicable. |
| `work_id` | `FixedSizeBinary(12)` | yes | Generational work/component handle when applicable. |
| `lease_revision` | `UInt64` | yes | Resource lease revision associated with the committed transition. |
| `transition` | `Utf8` | no | Stable transition token, from the owner-approved vocabulary. Candidate values are `queued`, `granted`, `preempted`, `resumed`, `restarted`, `completed`, `released`, `timed_out`, `cancelled`, and `aborted`. |
| `strategy` | `Utf8` | yes | Preemption strategy when relevant. |
| `preemptor_request_id` | `FixedSizeBinary(12)` | yes | Generational request handle causing preemption, when applicable. |
| `priority` | `Int32` | yes | Request priority after the operation, when defined. |
| `queue_len` | `UInt64` | yes | Queue length after the operation, when measured. |
| `active_count` | `UInt64` | yes | Active resource-use count after the operation, when measured. |
| `capacity` | `UInt32` | yes | Configured resource capacity at the transition, matching `ResourceCapacity.total`. |
| `elapsed_ticks` | `FixedSizeBinary(16)` | yes | Unsigned 128-bit elapsed ticks, little-endian, when applicable. |
| `remaining_ticks` | `FixedSizeBinary(16)` | yes | Unsigned 128-bit remaining ticks, little-endian, when applicable. |
| `cumulative_busy_ticks` | `FixedSizeBinary(16)` | yes | Unsigned 128-bit cumulative busy ticks, little-endian, when available. |
| `reason` | `Utf8` | yes | Owner-defined reason token for the transition. |

All handle fields use the existing 12-byte representation: `u64` index little-endian followed by `u32` generation little-endian. The fixed-size time fields use unsigned `u128` little-endian. A null means the value is inapplicable or unavailable for that transition; it is not zero or a sentinel. The owner must settle whether the candidate token vocabulary and numeric widths cover every Track 03/04 lifecycle case before adoption.

## Causal join and deterministic ordering

The primary row key is `(run_id, causal_event_id, transition_ordinal)` and must be unique. Each row joins to exactly one `event_log.v1` row by `(run_id, causal_event_id)`, represented there as `(run_id, event_id)`. A causal event may have zero or more transition rows. For a given event, ordinals are contiguous from zero and reflect the deterministic order in which committed resource transitions occur during that event. Producers must canonicalize any collection traversal that could otherwise affect this order.

A transition row is emitted only after its state change commits. An event-log record describes scheduler dispatch status; a lifecycle row describes a resource transition. They are distinct records and must not be inferred from one another or double-counted as the same outcome. A stale, cancelled or skipped **scheduler event** produces no lifecycle transition; a dispatched Flow cancellation command can still commit a request's `cancelled` lifecycle transition. A producer must not emit a transition for an event whose event-log row is absent, belongs to another run, or has status other than `dispatched`. Track 03 must define how directly admitted commands acquire a dispatched causal event before this join is adopted.

## Terminal and notification rules

For a lifecycle subject identified by the owner-approved resource/request relationship, at most one terminal transition may be recorded. Terminal candidates are `completed`, `released`, `timed_out`, `cancelled`, and `aborted`; the relevant owner must clarify which are mutually exclusive and how partially inserted or multi-resource requests are keyed before finalizing this rule. A transition stream must not append a second terminal row merely to signal a capacity change. In particular, `completed` must not be followed by a duplicate `released` record for the same terminal outcome. Capacity/lease effects belong in the committed transition's resulting measurements where applicable.

Notifications are delivery/observation messages, not state transitions. A notification does not add a lifecycle row by itself. If a notification corresponds to a committed transition, that transition is recorded once and notification delivery may refer to it using the agreed causal identifiers. Handlers observe committed state. A notification failure or retry must not duplicate a transition row.

## Owner decisions required

- **Track 03:** confirm lifecycle meanings, subject identity for terminal uniqueness, applicability of nullable handles, transition tokens, notification references, and the relationship between preemption and restart records.
- **Track 04:** own the final Arrow schema, encoding details, vocabulary stability, and implementation/round-trip evidence.
- **Track 01:** review handle and causal ordering assumptions and identify any core scheduler contract implications; no core type, ordering, or RNG change is proposed here.
- **Track 25:** review any public additive API and migration implications before implementation.
- **Track 22:** coordinate separately if checkpoint integration is available; this proposal creates no checkpoint representation or claim of save/restore support.

All decisions above remain pending. This document is a design proposal only and authorizes no runtime, Arrow, shared-contract, or checkpoint-format changes.
