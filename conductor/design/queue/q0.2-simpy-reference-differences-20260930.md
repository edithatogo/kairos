# SimPy 4.1.2 reference and Kairos design differences

**Pinned reference:** SimPy 4.1.2 resources API, accessed 2026-09-30: <https://simpy.readthedocs.io/en/4.1.2/api_reference/simpy.resources.html>.

This is a focused design comparison for the Q0 queue contract. It is not a claim of API compatibility or general simulator equivalence.

| Concern | SimPy 4.1.2 documented behavior | Kairos local contract | Classification |
|---|---|---|---|
| Capacity and claims | `Resource` has a bounded number of concurrent users; requests wait when full. Releasing succeeds immediately even when the process is not using it. | Claims are explicit ECS lifecycle records; cancellation/release handles have idempotent terminal behavior and generation checks. | Similar capacity intent; different lifecycle/error contract. |
| Priority queue | `PriorityResource` orders pending requests by ascending priority; lower numeric values are more important. `PriorityRequest.key` sorts by priority, request time, then preemption flag (preempting requests first at equal priority/time). | Queue ordering is ascending priority then immutable admission sequence (FIFO for equal priority); request flags do not reorder local admissions. | Priority direction shared; tie ordering intentionally differs. |
| Permission to evict | `PriorityRequest(preempt=True)` permits preemption on `PreemptiveResource`; `PriorityResource` does not use this flag to evict active users; the flag still participates in `PriorityRequest.key` ordering when priority and request time are equal. | Incoming `can_preempt` and an active claim's `preemptible(strategy)` are independent requirements. The victim must be strictly lower urgency; victim ties use least urgent, latest admission, then largest request ID. | Explicit consent and deterministic victim selection are local policies. |
| Interruption | A `PreemptiveResource` preemption interrupts the displaced process. `Preempted` provides the preempting process, resource and `usage_since`. | A victim follows one of Suspend (retain remaining work), Abort (terminal), or Restart (replay original sampled duration); Kairos records elapsed/remaining and cumulative busy work. | Kairos supplies domain-neutral recovery semantics not specified by this API. |
| Same-time completion/deadline | The cited resource API describes priorities and interruption; it does not define this contract's exact same-tick rules. | Work completing at T is materialized before eviction. A claim with deadline T cannot be granted at T. | Deliberate Kairos boundary semantics. |
| Zero-time work and loops | No equivalent per-tick loop budget is asserted from this resource API. | Zero-duration work grants and completes once at the same tick. The proposed FlowRuntime contract adds a finite per-tick transition budget alongside scheduler max-events; neither the per-tick setting nor structured outcome exists in the inspected runtime yet. | Planned Kairos safeguards; not attributed to SimPy and not implemented yet. |

## Source-backed details

SimPy documents `PriorityResource` as sorting pending requests in ascending priority, with lower values more important. `PriorityRequest` uses a key comprising priority, request time and the preemption flag. The preemption flag is meaningful only when the resource supports preemption; `PriorityResource` ignores it. `PreemptiveResource` interrupts a displaced process and provides `usage_since` in the interruption cause. Resource release is documented to succeed immediately regardless of whether the process currently uses the resource.

The per-tick budget row describes planned Kairos behavior, not shipped functionality. These statements describe the cited SimPy version only. In particular, the API reference does not supply Kairos' Suspend/Abort/Restart policies, strict-priority victim rule, victim tie-breaking, exclusive deadline boundary, complete-at-T-before-eviction ordering, or loop budget. Those remain the local contract and are represented by the accepted synthetic queue, boundary, and strategy fixtures.

## Zero-time bounds

Kairos permits a zero-duration claim to be granted and completed once at one simulation tick. Repeated same-tick continuations or notifications must remain bounded by the configured per-tick transition/notification limits and the existing maximum-event limit. The runtime must report the structured limit outcome rather than spin indefinitely. This design note does not set numeric defaults; those must be bound to the existing scheduler configuration and tested during runtime implementation.

## Scope limits

This is an API-reference comparison, not a differential execution test. It does not establish identical event scheduling, process semantics, race behavior, resource resizing, or all SimPy edge cases. Runtime conformance tests should exercise only the explicitly shared concepts; all differences above must use Kairos-local expected traces.
