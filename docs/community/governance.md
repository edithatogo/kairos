# Governance

Community governance for KairoECS is split between stable repo-level policy files and this public navigation page.

## Policy sources

| Topic | Source |
|---|---|
| Contribution rules | root `CONTRIBUTING.md` and `governance/CONTRIBUTING.md` |
| Code of conduct | root `CODE_OF_CONDUCT.md` and `governance/CODE_OF_CONDUCT.md` |
| Security reporting | root `SECURITY.md` |
| Maintainer expectations | `MAINTAINERS.md` and `governance/maintainer-ladder.md` |
| Decision-making | `GOVERNANCE.md` and `governance/decision-making.md` |
| Release authority | `governance/release-team.md` |
| Steering authority | `governance/steering-committee.md` |

## Community ladder

1. User
2. Contributor
3. Area reviewer
4. Maintainer
5. Release manager
6. Steering member

Promotion depends on sustained review quality, user care, reliability, and respect for the conduct policy. Code volume alone is not enough.

## Decision path

- Routine docs and example updates can be reviewed by the owning track or area maintainer.
- Public API, compatibility, packaging, registry, or release-timing changes require the relevant conductor track and governance review.
- Conduct and security reports use the root policy files, not public issue discussion.
- Unresolved cross-track disputes move to maintainers, then the steering path.

## Claim boundary

This page explains where governance lives. It does not replace the root policy files and does not grant package publication or API approval authority.
